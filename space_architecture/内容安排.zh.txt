Space 架构解析 · 如何设计一个高自由度的体素游戏（space_architecture）

【视频定位与创作意图】
本期视频以“游戏架构师与系统设计师”的第一视角，围绕在体素世界里创造作品的两类需求，对照社区的代表性模组，讲解 Space 的底层设计，以及每项设计的收益与代价：
- 需求一：造型。按尺度分层回应：体素地形 → 微体素精细建模 → 装饰体素自由造型，材质三层共用。
- 需求二：行为，即让作品动起来、受控制、能自动运转。依次回应：物理 → 控制 → 自动化。
每章结构统一为：需求 → 社区方案及其在 Minecraft 架构下的实现方式 → Space 的设计 → 代价。

【全片主线】
方块只负责形状，行为交给代码。原则本身对应两类需求：“方块只负责形状”= 需求一，“行为交给代码”= 需求二。这样分工的目的是性能与扩展性：在不牺牲自由度的前提下，让计算尽可能分布出去（多核并行，甚至放到玩家设备上运行），让同一个世界容纳更多玩家。少用体素是服务于这个目的的手段，在 02（一块斜板替代一大片微体素）出现；05 不设功能部件，首要原因是外观与逻辑解耦（利于分布式计算），减少体素只是其次，不再作为原则的一部分。
- 01 先用 Minecraft 原版讲清两类需求（造型：用方块、台阶、楼梯搭建筑；行为：用红石、活塞做自动门和自动农场），再引出把需求推得更远的代表模组，指出它们共同的宿主约束：造型和行为都要通过一米网格中的方块实现；Space 在引擎底层把造型和逻辑分开，由此引出原则，并说明分工的目的：性能与扩展性。方块描述形状和材质，地形按区块组织；实体可以带有自己的方块造型，由各自的代码控制行为；计算可以按区块、按实体拆开，交给多个处理器核心并行处理，实体还能分散到不同玩家的设备上运行；在不牺牲自由度的前提下让计算分布出去，容纳更多玩家。服务端集中计算与 tick 的对比留到 06 再讲。
- 02 造型一章按尺度由粗到细讲三层：地形要规模与性能 → 微体素补细节（对照 Chisels & Bits、LittleTiles，说明为何只做 8 等分）→ 装饰体素不对齐网格，可直接加在地形或实体上（对照 Yuushya Modelling）。03 材质收束前半部分。
- 04 物理（对照 Create、Valkyrien Skies），结尾抛出“悬挂、平衡与升力从何而来？”
- 05 代码：控制与自动化合为一章，“答案是代码”（对照红石、Create、Valkyrien Skies 附属的船舵、CC: Tweaked）。
  后半讲自动化：无人值守运转，以“区别在于计算发生在哪里”收尾。
- 06 运行机制单独成章：计算发生在哪里（对照 Minecraft 的服务端游戏循环与 tick），再讲运行权与服务器托管。它直接对应原则的目的（让计算分布出去），所以不并入 05。
- 07 用 50 架带旋转螺旋桨的飞机实测服务器物理负载和带宽 → 08 按两类需求回顾，收回原则。
- 物理 → 控制 → 自动化是递进关系：先有受力的刚体，控制才能施力；能被代码控制，才能无人值守地运转。全片列举时统一用这个顺序。

【口径要求】
- 只讲已实现并可演示的能力。
- 语体：专业、克制、陈述式。少用口语比喻和感叹，多用“需求—约束—设计—代价”的论证结构。
- 可用的专业词：刚体、质心、转动惯量、坐标系、网格对齐、碰撞查询、流式加载、服务端、沙盒。口播不出现“四元数”“WebAssembly”“AABB”“BVH”“执行租约”。
- 全片统一称“两类需求”：造型（建模）、行为（物理、控制、自动化）。不使用“三大支柱”。
- 主线原则只说“方块只负责形状，行为交给代码”，不再加“体素越少越好”；分工的目的统一说成“性能与扩展性：在不牺牲自由度的前提下，让计算尽可能分布出去，容纳更多玩家”。“多核”有依据：近处地形流式生成、远景地形 LOD 和微体素网格构建各在独立的 Web Worker 中运行，微体素网格的 Worker 数量随 CPU 核心数增加（engine/src/voxel/World.ts、MicroVoxelLayer.ts、render/DistantVoxelLayer.ts；client/docs/near-terrain-streaming.md）；实体这一侧，已实现的并行例子是服务器托管：每个实体一个独立进程、独占一个物理核心（client/README.md）。浏览器里的实体脚本目前在主线程运行，只有编译在 Worker 中（engine/src/scripting/EntityScriptRuntime.ts），所以口播用“可以交给多个处理器核心”，不要说浏览器里的实体物理或脚本已经是多核运行的，也不要报具体的玩家容量数字（Multiplayer V2 的每世界 32 人是规划目标）。
- 两类需求的范围：只针对“在体素世界里创造作品”，是我们归纳的分析框架，不是调查结论；不涵盖探索、生存、战斗、社交等需求。口播用“归纳为”，口播和画面都不要说成玩家的全部需求。依据：中文社区“建筑党”与“红石党 / 生电”的分法；Modrinth 的 19 个模组分类中，造型对应 Decoration，行为对应 Technology、Transportation、Game Mechanics（2026-11-11 查 api.modrinth.com/v2/tag/category）。
- 只讲真实差异：思路或实现相同的地方，直接说“同样 / 沿用同样的思路”；不要在对比之后再列双方共有的特性，暗示对方没有。已核对的相同点：装饰体素与 Yuushya Modelling 思路相同，在地形上都附着在方块上；微体素与 Chisels & Bits、LittleTiles 一样在原位雕刻；Valkyrien Skies 的飞船和 Create Aeronautics 的运动结构同样有独立坐标系（分别借船坞和 Sable 的 plot 实现）；CC: Tweaked 的海龟同样能探测、挖掘、铺设并联网通信；Space 的实体同样会读写共享的世界（对地形的修改经地形编辑通道同步）。真实差异只讲这些：装饰体素还能挂在实体上随实体运动、被脚本修改；物理由 Space 引擎原生提供，而 Minecraft 中由模组加入物理引擎；Create Aeronautics 为螺旋桨、热气球和车轮提供专门部件和升力计算，Space 不单独建模；CC: Tweaked 的计算机本身是方块；Minecraft 由服务端统一维护世界状态并集中计算，Space 的实体可以交给玩家的浏览器运行。
- 对比口径：只陈述各模组“解决了什么”以及“在 Minecraft 既有架构下如何实现”，把差异归因于宿主架构，而不是模组本身的优劣；不使用“落后、不足、更好、更强、更进一步”等评价词。对 Space 不如对方的地方（微体素精度只有 Chisels & Bits / LittleTiles 的一半）不回避，但口播不必说“一半”：先念出对方的十六乘十六乘十六，再念 Space 的八乘八乘八，差距由数字本身体现，画面上并排标出 16 与 8；紧接着说明这是现阶段的取舍并给出理由。理由按团队的实际权衡讲：网络带宽、存储、计算与艺术效果；这是现阶段的取舍，口播用“现阶段 / 目前”，不说成定论。
- 先从 Minecraft 原版讲起，再引出模组：观众未必熟悉模组，每个模组第一次出现时都配一句它做什么（口播一句，画面名字下再加一行说明）。
- 模组名称：口播与画面统一使用英文原名，不用中文译名，以免翻译后感到陌生：Chisels & Bits、LittleTiles、Yuushya Modelling、Create、CC: Tweaked、Valkyrien Skies、Eureka!（Valkyrien Skies 附属）、Create Aeronautics（Create 附属）、Sable（Create Aeronautics 依赖的物理库，口播不提）。红石是原版机制而非模组，保留“红石”。
- 统一说“体素世界”，不说“方块世界”。
- 术语“代码”和“脚本”按层次分工（2026-11-13）：“代码”只用于原则这一层，与方块和形状相对，例如“方块只负责形状，行为交给代码”、章节标题、“答案是代码”、“逻辑写在各个实体的代码里”；“脚本”指挂在组件上、具体编写和运行的东西，例如“挂载一段脚本”“驾驶脚本”“脚本运行在沙盒中”，与引擎界面的 Script 一致。原则不说成“行为交给脚本”：中文游戏语境里“脚本”常指挂机脚本或外挂。08 回顾时说“行为交给实体与脚本”，因为物理由引擎提供，不是玩家写的代码。CC: Tweaked 保留它自己的“程序 / 编程”。
- 第二类需求统一叫“行为”，不改成“运动控制”：行为包括物理、控制与自动化，铺路机、雷达塔和红石农场都不是运动控制；“运动控制”还是一个现成的工程术语，含义更窄。首次出现时用“让作品动起来、受控制、能自动运转”说明。
- “服务端集中计算”指 Minecraft 的逻辑服务端；单人游戏时它是本机内置的服务端。口播不展开，字幕可注明。
- 装饰体素参与碰撞，但不计质量（2026-11-12 起，引擎提交 deea151）。碰撞按 0.125 m 构造网格近似：不旋转或按直角旋转的装饰是一个对齐网格的盒子；任意角度旋转的装饰，碰撞是 0.125 m 一级的台阶；超大的旋转装饰（约 8 m 以上）台阶更粗。质量、转动惯量、质心、座椅和约束都不计入装饰。可以拍玩家站在装饰板上，但别给斜面拉近特写，免得“外观平滑、碰撞是台阶”看起来像 bug；口播不解释这一点，只在字幕里注明。不要再说“装饰体素只参与显示”。录制前确认线上版本已包含这项改动（提交时在 feat/decoration-collision 分支上）。
- 装饰体素可以直接加在地形上（2026-11-12 起，引擎提交 4a8acaf），不要再说“只存在于实体中”。组装和解体都会带上装饰体素：组装时，被框选标准方块上的装饰移到新实体上；解体时，实体的装饰绑回最近的标准方块，世界中的位置和朝向都不变。组装这一半是 2026-11-12 修好的，录制前要确认线上版本已经包含；用微体素框选组装时，方块会被细分，上面的装饰仍会移除。
- 不做红石 / 传动部件、不单独建模空气动力学与轮胎，是主动的设计取舍。不做功能部件，首先是为了外观与逻辑解耦，逻辑写在各个实体的代码里，计算以实体为单位，可以整体交给不同设备，因此放弃 Create 式的传动机制和红石式的控制系统，其次才是减少体素数量；不建模空气动力学与轮胎，口播不讲“规则统一”这类理由，只说明外观用组件树搭出、推力与升力交给代码；代价只讲放弃传动与红石控制，以及升力不会自动产生；口播不提“需要写代码”，也不提 Agent Build。
- 口播里的数字只留最关键的：一米、十六乘十六乘十六（对照）、八乘八乘八、十二点五厘米、二十四位色，以及 Minecraft 的“每秒二十次”和“五十毫秒”（06 讲 tick 时用）。512、4,096、1,024、每区块 256 个装饰体素、16 m、20 Hz、每个实体 64 个组件 / 16 层、每个浏览器 8 个运行中实体等放画面字幕。
- 网址和 WebGPU 要求只上屏，不念出来；口播也不说“体验链接在简介中”（2026-11-13 用户要求删除）。
- 运行权是抢占式的（托管除外）：运行权空出时，谁的浏览器先申请到谁运行；持有者持续续期期间独占，其他人（包括作者和管理员）不能停止或修改；持有者可以随时手动停止，立即释放运行权，停止后的实体不会被自动接手，之后谁先重新启动谁运行；运行者离开、掉线或停止续期后，附近玩家的浏览器立即抢占。托管的实体运行权固定在服务器上，不参与抢占。“抢占”指抢先拿到空出的运行权，不要说成可以从正在运行的玩家手里夺走：服务端只在租约过期或同一终端续期时才授予运行权（server/routers/space_entities.py claim_world_entity_execution_leases）。
- 06 的分布式运行只讲已实现的部分：一位玩家的浏览器独占运行实体、结果经服务器实时转发、其他人只插值显示、运行者离开后附近玩家自动接管、可交给服务器托管。P2P 尚未实现，口播和画面都不提。
- 服务器托管按 credit 计费，但口播和画面都不提计费：不报价格，不拍预算对话框。口播也不提托管实体独占一个处理器核心，画面不特写核心编号（2026-11-13 用户要求）。
- 解体不展示：口播和画面都不出现解体（2026-11-13 用户要求）。组装与解体如何处理装饰体素，只作为背景事实保留。

【口播用到的事实与来源】
- Chisels & Bits：把方块分成 16×16×16 的小立方体逐格雕刻。来源：MC百科 mcmod.cn/class/806.html
- LittleTiles：小块可细到普通方块的 1/4096（16³），也可更细（MC百科写 1/32768 或更小）；小块能组合成门、椅子、梯子、储物、滑动门等功能结构。来源：modrinth.com/mod/littletiles、mcmod.cn/class/1601.html
- Yuushya Modelling：Yuushya Townscape 的联动模组，把方块转为方块实体后，对模型做移动、旋转、缩放，一个位置可展示多个模型。Yuushya Townscape 对同类功能的说明是“本质上还是方块”、可移动范围为原位 ±1 格。来源：modrinth.com/mod/yuushya-modelling、mcmod.cn/class/11555.html、mcmod.cn/item/539244.html
- Create：本体的动态结构由轴承、活塞、龙门、矿车与列车等驱动，沿预设的轴或轨道运动，不是受力驱动的刚体。（通用知识，成片前可再对照官方 Wiki 核一次）口播要说“Create 本身”，因为附属模组 Create Aeronautics 已经带来刚体物理。
- Create Aeronautics（Simulated Team）：Create 的附属模组，基于物理库 Sable 构建飞机、无人机、热气球、汽车等载具与物理结构；分 Simulated（组装、红石部件与工具）、Aeronautics（热气、螺旋桨、漂浮石）、Offroad（车轮）三部分。Sable 把可运动的方块区域做成“sub-level”，组装后仍可交互；物理管线基于 Rust 编写的 Rapier 物理引擎，带升力计算。sub-level 的方块存放在各自的 plot 里，再变换到世界坐标（实体落进 plot 时会被“踢”回全局空间），与 Valkyrien Skies 的船坞做法相近。来源：modrinth.com/mod/create-aeronautics、modrinth.com/mod/sable、github.com/ryanhcode/sable/wiki/Working-with-Entities（2026-11-12 查）
  推力与升力（2026-11-13 查 MC百科）：螺旋桨轴承把面前含风帆类方块的区域组装成螺旋桨结构，接入 Create 的旋转动力后与空气作用，产生垂直于桨面的推进力；推力随转速、所在高度的气压和风帆数增加，随机身沿桨轴方向的速度增大而减小，消耗应力（mcmod.cn/item/937936.html）。热空气燃烧室接红石信号后向上方密闭的热空气气囊供气，产生升力，单个燃烧室设定体积 5–500 m³（mcmod.cn/item/937902.html）。另有浮空水晶（“魔法浮空石”）提供浮力，越野部分提供各种轮胎（mcmod.cn/class/26350.html）。
- Valkyrien Skies：提供完整的物理引擎，飞船作为刚体，考虑重量、摩擦与弹性；飞船方块存放在离出生点数百万格的“船坞”（Shipyard），再投影到世界中，让方块以为自己仍对齐网格、从而正常工作；物理线程配置位于服务端配置 vs_core_server.json（默认每游戏刻 3 个物理刻，即 60 Hz）。驾驶依赖附属模组，例如 Eureka! 的船舵。Valkyrien Skies 本身不产生推力：Eureka! 的船舶引擎提供动力，气球提供升力，浮子提供水上浮力，压载调节姿态，船舵负责组装与转向（mcmod.cn/class/8007.html 及其物品页，2026-11-13 查）。来源：valkyrienskies.org/wiki/Valkyrien_Skies、/wiki/Config、modrinth.com/mod/valkyrien-skies、mcmod.cn/class/1528.html
- CC: Tweaked：在游戏内加入可编程的计算机、显示器、网络与海龟机器人；程序通过红石、外设与海龟机器人和世界交互，运行在服务端（存在纯服务端运行的补丁即可佐证）。来源：mcmod.cn/class/1681.html、mcmod.cn/class/6723.html
- 红石：原版机制，信号沿相邻方块逐格传递，在服务端按游戏刻计算。红石自动农场无人操作也会运转，但只在已加载并处于模拟状态的区块里：玩家周围模拟距离以内（外加一圈区块，红石仍会运行），或用 /forceload 强制加载、传送门正在加载的区块；出生点区块在 1.21.9 中已移除。玩家走远、区块卸载后，机器就停下。来源：minecraft.wiki/w/Chunk（2026-11-13 查）。这和 Space 的浏览器运行一样（附近有玩家才运行，托管相当于强制加载），是共同点，口播不拿来对比，也不说红石“在后台一直运行”。
- 游戏刻（tick）：Minecraft 由一个游戏循环推进，固定每秒 20 次（每次 50 ms）；服务端每个 tick 依次处理各维度的区块、计划刻、方块事件、实体和方块实体。单个 tick 用时（MSPT）超过 50 ms 时，每秒 tick 数（TPS）下降，而游戏中的大多数过程按 tick 计时，于是整个世界一起变慢。常见的服务端卡顿来源包括红石元件（大量方块更新）、漏斗和大量生物的 AI。来源：minecraft.wiki/w/Tick（2026-11-12 查）。注意：CC: Tweaked 的 Lua 程序在自己的计算机线程里执行，Valkyrien Skies 的物理在单独的物理线程里运行，两者都不算在这个循环里，口播不要把它们说成在 tick 里依次计算。

二、两类需求与 Space 的对应设计
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【需求一：造型（按尺度分层）】
1. 地形层：标准体素
   - 1 m 标准体素，严格对齐网格，负责山体、地基与建筑主体。
   - 取舍：规整网格让碰撞查询、存储与大世界流式加载保持高效，也是精细层的基础。
2. 精细层：微体素
   - 单个标准方块细分为 8×8×8 = 512 个微体素，每个 0.125 m，用于窗框、倒角、扶手与精雕。
   - 与标准体素同一坐标系共存（Chisels & Bits、LittleTiles 也是在原位雕刻，这不是区别，口播不提）。
   - 取舍（现阶段，后续可能调整）：地形微体素每边细分只有 Chisels & Bits / LittleTiles（16 等分）的一半。地形上的每处雕刻都要持久存储、参与碰撞计算，并经网络同步给其他玩家；16 等分时每个方块 4,096 个微格，数据量是 8 倍。团队综合网络带宽、存储、计算与艺术效果四项权衡，暂定 8×8×8。微体素碰撞按 2×2×2 m 分区缓存（合并碰撞盒 + BVH，每区最多 4,096 个微格）。更高的造型自由度交给装饰体素，而不是继续加密网格。（引擎依据：engine/README.md、src/voxel/MicroGrid.ts）
3. 自由层：装饰体素
   - 不受网格对齐约束。建模工具可以把它加在地形的标准方块上，也可以加在实体上。
   - 地形上：绑定一个一米标准方块（锚点），存放在该方块所在的区块，随地形编辑批次（set_decoration / remove_decoration）和区块快照存储、同步；每个 16×16 m 区块最多 256 个，偏移与尺寸每轴不超过 16 m；方块被挖掉或细分为微体素时一并移除；微体素不能挂装饰。复制 / 剪切、背包、市场的方块组都会带上装饰（每组最多 4,096 个），放置时随方块一起旋转。（依据：引擎提交 4a8acaf；client/CHANGELOG.md「2026-11 — Terrain decorations」；engine/src/constants/SpaceConstants.ts）
   - 实体上：随实体运动，可被脚本在运行时修改（self.decorations.upsert）；每个实体最多 1,024 个。
   - 地形与实体之间：解体时，实体的装饰体素绑定到最近的、刚写回的标准方块上，保持世界中的位置和朝向；超出 16 m 限制或区块已满的会被跳过，并提示数量。组装时，被框选标准方块上的装饰先读出来，再移到新实体的根组件上，保持世界中的位置和朝向；超出每个实体 1,024 个上限的会被跳过，并提示数量。微体素框选会细分方块，装饰仍按地形规则移除。（engine/src/contraption/ContraptionManager.ts assembleSelection / adoptTerrainDecorations，2026-11-12 修复，引擎提交 105be60）
   - 任意角度旋转：基于四元数，没有固定档位，可做掠翼、倾斜装甲、流线型挡风玻璃。
   - 三轴独立缩放：X / Y / Z 独立（单轴最大 256），可压成薄导流板，或拉成液压杆、天线。
   - 接主线：一块缩放后的斜板，可以替代一大片微体素。
   - 碰撞：实体和地形上的装饰体素都参与碰撞。碰撞形状是装饰在 0.125 m 构造网格上的投影：轴对齐的装饰是一个盒子；旋转的装饰取中心落在其内的网格单元，斜面变成 0.125 m 的台阶；单个旋转装饰超过 4,096 列扫描（约 8 m）时改用 2、4、8… 格的粗网格。实体装饰的碰撞并入实体的合并碰撞盒，随脚本的实时修改更新，组件关闭碰撞时一并忽略；地形装饰对实体和玩家都像地形一样碰撞，改动会唤醒附近休眠的刚体。服务器托管的模拟也会加载区块装饰。（依据：引擎提交 deea151；client/docs/formats.md「Decoration collision」；engine/src/physics/DecorationCollision.ts、engine/src/voxel/TerrainDecorationCollision.ts）
   - 代价一：碰撞是近似的，平滑斜面在碰撞上是 0.125 m 台阶，和微体素共用同一套网格。
   - 代价二：不计质量，不改变质量、转动惯量、质心、座椅与约束；质量分布只由方块决定。
   - 代价三：地形上的装饰体素依附于所属方块，方块被挖掉或细分时一并移除；每个区块有数量上限。
4. 材质（三层共用）
   - 标准体素、微体素、装饰体素都支持独立 24-bit 颜色（0xRRGGBB）。
   - 普通材质：漫反射。
   - 自发光材质：自带泛光（引擎内为 1.5 倍亮度，VOXEL_EMISSIVE_INTENSITY = 1.5；口播不报数字），无需另放光源。
   - 半透明材质：透明度 1%–100% 连续可调（口播不强调连续调节，也不念范围）；前后重叠时层次正确（成片前对照实拍确认）。

【需求二：行为（物理 → 控制 → 自动化）】
1. 物理：实体化与刚体
   - 地形 ↔ 实体双向转换：选择框圈定任意体素切片 → 组装（assemble）为拥有局部坐标系的独立实体；停稳后解体（disassemble），原样写回地形。实体由引擎原生表示，不需要把方块搬到别处再投影。
   - 刚体：根据方块分布自动计算质心与转动惯量；响应重力、推力 / 力 / 力矩、碰撞反作用力与摩擦。
   - 组件树：实体停止时，用选区工具框选实体内的方块，按 G（Assemble Sub-Contraption）就把它们拆成一个子组件。组件逐级挂接成树，每个实体最多 64 个组件、最多 16 层。子组件可以是运动学刚体（由脚本直接设定相对父组件的位置、朝向或转速），也可以是动力学刚体（受力运动，用 point / hinge / weld 约束与父组件或世界相连）。Selector 用白色连线标出组件与枢轴的关系，组件描边逐级黑白交替。（依据：client/README.md「Assemble Sub-Contraption」与 Selector 说明；server/space/agent/entityAPI.md「Kinematics」「Rigid body, constraints, and Stop」；engine/src/constants/SpaceConstants.ts MAX_ENTITY_COMPONENTS、MAX_ENTITY_HIERARCHY_DEPTH）
   - 设计取舍：引擎只提供通用刚体物理，刻意不为空气动力学、轮胎等单独建模。通用刚体物理的范围（2026-11-13 核对 engine/src/physics/ContraptionPhysics.ts）：重力、力 / 力矩、碰撞（含弹性系数与摩擦）、统一的线速度 / 角速度阻尼、point / hinge / weld 三种约束、休眠与唤醒；没有浮力、空气动力学、车轮或悬挂模型。阻尼对所有方向一视同仁，不会产生升力。口播用“只提供”，不用“只保留”（引擎并没有删掉什么）。好处：规则少而统一（口播不讲）。代价：升力不会自动产生，悬挂、平衡、升力都要由脚本施力实现。
2. 控制：用代码直接施力（不用红石或传动部件）
   - 设计取舍：首先是外观与逻辑解耦。红石线路、齿轮、传动轴、船舵与引擎方块这类功能部件，把逻辑做进了方块，必须和周围的方块一起在共享的世界里计算；Space 不设这类部件，方块只负责形状，逻辑写在各个实体的代码里，计算就能以实体为单位，整体交给不同的设备（见 06 的 tick 对比）。口播不用“才能”：真正妨碍分布的是放在地形里、靠相邻方块连通的逻辑（红石线路、传动轴可以跨越地形和多台机器）；实体对外只通过明确的接口交互：读写世界（编辑由服务器校验）、实体间消息、与其他实体的插值副本碰撞。2026-11-13 核对：client/docs/networking.md（执行端独自推进脚本、重力、力与约束，bodies 每个组件一项）；server/routers/space_entities.py 的运行时快照（变量、时钟、子组件姿态）随实体在执行端之间转交。代价是放弃 Create 式的传动机制和红石式的控制系统。其次，这样也减少了体素数量。口播不讲“需要写代码”这一代价，也不提 Agent Build。
   - 每个组件都可挂载 AssemblyScript 控制脚本（根组件的脚本先于子组件运行，self.child(id) 取得子组件），编译为 WebAssembly，在沙盒中运行（无网络、文件系统、DOM）；加载他人分享的作品同样安全。
   - 输入：座椅 / 驾驶者、按键按下与松开、点击方块、实体间消息。
   - 输出：applyThrust / applyForce / applyTorque 直接施力，驱动子组件的相对运动（运动学子组件用 setLocalPosition / setLocalRotation / setLocalSpin、setSpin*RPM；动力学子组件用力、力矩与约束），切换材质（如点亮车灯），向其他实体发送消息。
3. 自动化：无人值守运转与分布式运行
   - 节拍：脚本每秒运行 20 次（实体 tick），物理每秒 60 次，都在运行者自己的设备上计算；某个组件超出时间、燃料或内存预算时，只会停止这一个实体（server/space/agent/entityAPI.md）。所以一台机器再重，也只占用运行它的设备，不会拖慢整个世界。
   - 脚本能力：每个实体 tick（20 Hz）都会运行，不需要玩家输入。可读取世界方块与微体素、射线检测、查询附近 64 m 内的实体；可放置 / 清除 / 上色地形中的标准体素与微体素；可向其他实体发送消息协同工作；可把选区组装成新实体。（依据：server/space/agent/entityAPI.md）
   - 设计动机：在 Minecraft 的架构下，红石、Create、CC: Tweaked 和 Valkyrien Skies 的物理都要读写共享的世界状态，由服务端集中计算。Space 的实体是自包含的（方块 + 刚体 + 脚本状态），可以整个交给一个终端运行。
   - 执行权：每个运行中的实体同一时刻只由一个浏览器运算脚本与物理（8 秒执行租约，持有者持续续期；租约有效期间按终端独占，作者和管理员也不能停止或夺走；过期后由最先申请的附近浏览器抢到；持有者 Stop 时，服务端立即清空执行者与租约并把执行代次加一，停止后的实体不会被自动接手，谁先重新启动谁获得运行权（server/routers/space_entities.py run-state 处理））。其他浏览器只接收位置、姿态（四元数）与线 / 角速度，插值显示可碰撞的代理，不运行脚本、不计算受力。
   - 同步：WebSocket + MessagePack 实时中转，20 Hz 发送变化的位姿；脚本对地形的修改走地形编辑通道同步给所有人；服务器不跑物理。每 6 秒的运行快照只用于恢复，不走实时通道。
   - 接管：运行者走出范围或下线后租约过期，附近仍加载着该实体的浏览器会自动申请租约，接着运行。
   - 托管：同一个实体可交给服务器托管（独立进程、独占一个 CPU 核心，按 credit 计费）；此时没有浏览器执行者，其他人同样只接收结果。任何世界成员都可以托管未被占用的实体；托管前，正在运行它的浏览器必须先停止（发起托管的浏览器会自动停止自己的运行，但不会停止别人的）。只有发起托管的账号能修改或停止托管，提前停止会保留未用完的预付时长，实体回到可编辑状态。核心池全局共 128 个，且不超过实际物理核心数；托管实体另有限制：最多 512 个方块、8 个组件、活动范围有限。服务器每秒提交一次状态、地形修改与计费，位姿以 20 Hz 转发给其他人。（依据：server/docs/entity-hosting.md、server/docs/space-backend.md、client/docs/networking.md）
   - 上限（放字幕）：每个浏览器最多同时运行 8 个、每个世界最多 64 个实体。
   - 代价：实体只在有玩家的已加载区域运行，附近没有玩家时，未托管的实体会暂停。
   - 尚未实现：P2P 同步。因为只需转发结果，架构上对点对点友好；口播和画面都不提。
   - 引擎依据：entropydrop_space 仓库 server/docs/space-backend.md、client/docs/networking.md、client/src/engine/network/SpaceEntitySync.ts、server/docs/entity-hosting.md。

【06_runtime】07:15 - 08:55（100秒）
- 标题：运行机制：计算在哪里发生
- 画面：按“计算在哪里 → 运行权 → 托管”推进；沿用 05 的铺路机作为演示实体。
  1. tick 对比示意（“Minecraft 的整个世界由服务端的一个游戏循环推进”起）：对比示意：左边，红石、Create 装置和各种实体排成一列，依次进入服务端的同一个游戏循环（标“每秒 20 tick · 每 tick 50 ms”），其中一台机器变重，整条队伍变慢，所有玩家画面一起卡顿；右边，几个实体分别落在不同玩家的设备上运算，服务器居中只转发位姿与地形修改。
  2. 运行权：运行权（双人分屏实拍，需两个账号）：玩家 A 启动铺路机，实体名牌第二行显示执行者 A；玩家 B 画面里同一台机器同步工作。说到“独占运行权，其他人无法停止或修改它”时，B 尝试停止或编辑这台机器，画面出现被拒绝的提示（录制前确认提示文案）。说到“运行者可以随时手动停止”时，A 停止机器，名牌上的执行者消失，B 随即启动它，执行者变为 B。说到“附近玩家的浏览器立即抢占”时，B 再启动后走远或退出，几秒后名牌上的执行者切换回 A，机器继续运转。
  3. 服务器托管：服务器托管：在实体右键菜单点 Host…，预算对话框不入镜，直接切到托管生效后的画面；Authority 面板显示改由服务器执行；HUD 的 Hosted Entities 列表显示这台机器（核心编号裁掉或不特写）；A、B 都离开后，用第三个视角（或重新进入）确认机器仍在运转。录制前确认环境已开启托管，确认预算会消耗 credit。
- 字幕：只同步结果：位置 · 姿态 · 速度（20 Hz）+ 地形修改 · 运行权：8 秒租约，由运行者的设备独占并持续续期 · 每个浏览器最多同时运行 8 个实体 · 托管：每个实体一个独立进程。
- 叙事核心：承接 05 结尾的“区别在于计算发生在哪里”。本章对应主线原则的目的：让计算分布出去，容纳更多玩家，所以单独成章。Minecraft 的整个世界由服务端的一个游戏循环推进（每秒 20 个 tick），红石、Create 装置与实体在其中依次计算，单次 tick 超过 50 ms 整个世界变慢、所有玩家一起卡顿；Space 的实体自包含，整体交给一位玩家的浏览器运行，各自按自己的节拍计算，再重也只占用运行它的设备，只同步结果。运行机制讲三点：以“实体交给谁运行？”过渡（不说“具体来说”）；默认情况下（即没有托管时），运行权靠抢占，谁先启动或先申请到谁运行，独自计算，其他人只插值显示；持有者续期期间独占，其他人不能停止或修改；持有者可随时手动停止，立即释放运行权，之后谁先重新启动谁运行；运行者离开或掉线后运行权几秒内空出，附近玩家的浏览器立即抢占。需要不间断运行的实体交给服务器托管，运行权固定在服务器上，不再参与抢占：独立进程、同一套引擎；口播不提计费，也不提独占处理器核心。附近没有玩家时实体会暂停，这一点口播不提。

- 标题：性能测试
- 测试问题：每位玩家驾驶一架飞机。48、64、96 名模拟玩家分别同时盘旋、交会，游戏还能流畅运行吗？

- 测试：版本 e0d451d，三档各两轮，每轮 500 步，目标 20 Hz。每名模拟玩家控制一架飞机，由真实 WebSocket 中继接收同组飞机的姿态。Rapier 处理了全部物理子步。画面用第 04 章机型、Nature 地图、Ultra 和 Medium 泛光重新录制，源轨迹来自单独补录的 96 架全 Rapier 联跑。
- 工作量：单架约 2.2 万体素、575 个合并碰撞盒。96 架合计约 209 万体素和 5.5 万碰撞盒，其中约 90 万体素有外露面，按相机裁剪前的模型统计。螺旋桨以 128 rpm 旋转并参与碰撞，96 架两轮均有 48 组中的 16 组实际接触。
- 三档联跑结果（CPU 占用率按分配的 96 个物理核心平均）：
  - 48 架，平均 20.0 步/秒，整批单步 P95 30.0–36.8 ms，1 / 500 步超过 50 ms，执行端平均 CPU 占用率 8.9–9.0%。
  - 64 架，平均 20.0 步/秒，整批单步 P95 29.3–41.3 ms，1–3 / 500 步超过 50 ms，执行端平均 CPU 占用率 11.8–12.6%。
  - 96 架，平均 20.0 步/秒，整批单步 P95 42.6–43.0 ms，9–11 / 500 步超过 50 ms，执行端平均 CPU 占用率 21.7–21.9%。
- 转发内容：执行端每帧上报机身与螺旋桨各自的完整姿态，包括绝对世界位置、朝向、线速度和角速度。服务端每轮按实体选取最新帧，并把附近飞机的多条姿态合为一包。客户端通过实体定义单独加载体素模型，再对姿态插值，移动和旋转本地模型。示例取第 37 号飞机，第 147 帧，机身位置为 5186.8 / 139.8 / 892.4，螺旋桨位置为 5192.3 / 142.1 / 889.3。
- 同步带宽：96 架联跑时服务器平均接收 11.71–11.79 Mbps、发送 12.29–12.61 Mbps，按两轮范围，包含 WebSocket 和 TCP 开销。
- 结论：本次测试验证了分布式执行端计算自机碰撞、服务器同步姿态的架构，可以支撑这组高负荷多人飞行。数据适用于该机型、双机编组和同机隔离条件。
